## 三、最值钱的一个发现：ReplayLab 的 8 格采集有硬件级缺陷

这条是本次评估挖出来的，**README 和项目记忆里的描述都不准确**。

### 现象

跳绳用正确的视频（`rope8_4k.mp4`）重跑后，仍然 `area6 = 0`，极差 136：

```
轮 0: 1:116,2:117,3:108,4:121,5:122,6:0,7:128,8:136 | 极差=136
area6: 有效轮=1 准确率 0.0% | inArea=100%
```

### 根因（证据链完整）

深挖原始采集数据 `rope_20260914_161300.jsonl`（7080 采样点）后确认：

**area6 从未进入 `SPORTING` 状态，全程停在 `DEFAULT_STATUS`（6858/6858 次采样）。**

| area | 进入 SPORTING | 运动时长 |
|---|---|---|
| 1 / 2 / 3 | t=7.52 | 66.35s |
| 4 / 5 / 7 / 8 | t=7.52 | 66.13s |
| **6** | **从未出现** | **0** |

**三条排除性证据**：

1. **不是没人** —— area6 的 `in` 字段 6858 次采样**全是 true**，设备自己认为格子里始终有人；
2. **不是 tid 串号** —— `tid → area` 严格一一对应，area6 独占 `tid=10`，无人抢号；
3. **不是脚本问题** —— area6 有 6858 个采样点，采集量与其他各路（6858~6862）持平。

**关键对照**：同一台设备、同一套流程跑开合跳，**8 路全部在 t≈74.2~74.9 进入 SPORTING，没有一路掉队**。

→ 所以采集链路、拼贴视频、流水线部署逻辑都是好的，问题**特异性地落在跳绳项目（itemId=17）的 area6 点位配置上**。

### 为什么重要

- 它同时解释了 `极差=136` —— 极差完全由这一路贡献，不是真实的一致性问题；
- 它意味着 ReplayLab 目前的跳绳数据**不能作为准确率结论使用**；
- 而开合跳（itemId=28，准确率 101.1~103.0%、极差 1~6、inArea 93~96%）是**健康**的，可以信。

### 影响面

ReplayLab 是"用视频注入替代真人实拍"的平台，**8 格同源拼贴是它的核心提效手段**（一次测试覆盖 8 路）。
如果 8 格里的格子会随机性地不工作，那这个核心手段的可信度就要打问号 —— 而目前只有 2 个项目跑过，
开合跳正常、跳绳异常，**样本太少，无法判断是"跳绳专用问题"还是"8 格通用缺陷"**。

完整诊断已落盘：`ReplayLab/reports/_诊断_rope_area6失败_20260917.md`

## 四、第二个短板：E2E 的"用例"其实是"录制"

`E2E/tests/rope/` 下 22 个文件，差异**仅在时间戳与学校名**。而唯一的 golden 比对用例
（`test_rope8_1m_20260910_golden.py`）里，最关键的那一步断言是注释掉的：

```python
# TODO: 日志解析出本次回放的 8 路成绩 replay_scores
# for i, (got, base) in enumerate(zip(replay_scores, golden['scores'])):
#     assert abs(got - base) <= TOLERANCE, ...
pytest.skip("日志成绩解析待接入后启用比对；golden 基准已就绪: " + str(golden['scores']))
```

也就是：**golden 基准（125/138/102/115/127/153/139/138 → 1726）已经备好了，
但从日志里把成绩解析出来的那一步没接上**。这导致 E2E 目前跑完只证明"流程没崩"，不证明"算法对"。

对比之下，ReplayLab 的采集+分析链路是通的（能算出准确率），**两者的能力可以互补**。

## 五、下一步：三个候选方向

### 方向 A：修 ReplayLab 的 8 格采集缺陷 ⭐ 建议优先

**为什么**：这是唯一一个"结论不可信"的技术性缺陷，且它污染的是平台最核心的产出（算法准确率）。
不修，后面所有"准确率提升/回归对比"都是建在沙子上。

**做什么**：
1. 读设备 `item.json` 的 `item17.init_area`，检查 area6 的归一化坐标是否越界/退化；
2. 做差分实验（把 area7 的点位抄给 area6，看是否立刻正常）；
3. 若坐实点位问题，修正 `items.json` / 部署逻辑，重跑验证。

**前置条件**：需要真机（192.168.2.60）+ 一次约 800s 的采集。**需要你确认能否占用设备。**

---

### 方向 B：把 E2E 的成绩比对接上 ⭐ 与 A 互补

**为什么**：golden 已就绪，只差"从日志解析成绩"这一步。接上后 E2E 就能做真正的精度断言，
且**与 ReplayLab 是两条独立路径**（E2E 走真实 APP 发令 + 真机回放，ReplayLab 走注入），
两条路径交叉验证比单条更有说服力。

**做什么**：参考 `Log/analyze_camera_Latest.py` 的成绩提取逻辑，按点位/人员归组，
产出 `replay_scores` 填进那个 TODO。

**优势**：不需要额外设备时间（可离线开发），可以先做。

---

### 方向 C：凭据轮换（安全债）

`docs/CREDENTIAL_ROTATION.md` 里 9 项泄露清单、5 步轮换顺序都已写好，但**一步都还没执行**。
仓库里已清理干净，但**只要口令本身没变，曾拿到过文件的人依然能登录**。

**最低风险入口**：第 1 步云平台账号（`huangpu`，平台网页改，可自行回滚）。
**最高风险项**：第 3 步设备 SSH 口令（改错会锁死设备，手册要求保留一个已登录会话兜底）。

---

### 方向 D：CI + 报告趋势（长远）

现状：无 `.github` / `Jenkinsfile` / `tox.ini`，全部手工触发；每批次报告独立，**无跨固件趋势对比**。
这一层做完，"固件 A vs 固件 B 谁更好"才能自动答上来。依赖 A/B 先把数据可信度解决。
